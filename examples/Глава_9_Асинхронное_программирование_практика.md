# Глава 9 «Асинхронное программирование» — теория, примеры и практические задания

Этот файл дополняет `book/Глава_9_Асинхронное_программирование.md`. Каждый раздел содержит:
- **Теория** — сжатый конспект соответствующей части главы (номера листингов — по книге);
- **Примеры** — код с разбором; полные версии лежат в `src/c9.rs` (функции `fX_Y`) и запускаются через `cargo run`;
- **Задания** — упражнения для самостоятельной работы (от простых к сложным). Решения кладите в `src/c9.rs` как `eX_Y()`.

**Главное правило этой главы: никаких внешних крейтов.** Tokio и `futures` прячут ровно то, что глава объясняет. Поэтому `Future`, `Waker`, `block_on`, `join` и исполнитель со `spawn` мы собираем сами, только на `std`. Когда всё это написано руками, tokio уже не выглядит магией.

Карта главы:

```
async fn / async {}  ──компилятор──▶  генератор (машина состояний, enum)
        │                                   │ impl Future
        ▼                                   ▼
   .await = loop { poll; yield }     poll(self: Pin<&mut Self>, cx: &mut Context)
                                            │            │
                       Pin/Unpin: самоссылки ┘            └ Waker: «эту задачу снова можно опросить»
                                                                 │
                исполнитель (executor) ◀── wake ── листовая футура / реактор (epoll, таймеры)
                     │
                 spawn: корневая футура = задача (task)
```

## 1. Poll и трейт Future

### Теория

- **Синхронный (блокирующий)** вызов не возвращается, пока операция не закончится. Поток всё это время спит в ядре. Чтобы ждать несколько вещей сразу, нужно несколько потоков. Потоки дают **конкурентность**, но вместе с ней и **параллелизм**: отсюда обязательные `Arc`/`Mutex`, дорогие переключения контекста и «по потоку на каждое ожидание».
- **Асинхронный (неблокирующий)** интерфейс сразу отвечает: «вот результат» или «приходи позже». В Rust это `enum Poll<T> { Ready(T), Pending }` (листинг 9-1). Метод `poll` делает всё, что может сделать без блокировки, *запоминает, где остановился*, и возвращает управление.
- Конкурентность ≠ параллелизм: `_-_-_-` (задачи чередуются на одном ядре) против `=====` (задачи идут одновременно). Async даёт первое без второго, если вы сами не попросите второе.
- Чтобы не изобретать `poll_recv`, `poll_keypress` и т. п. для каждого API, опрос стандартизирован трейтом `Future` (листинг 9-2, упрощённо; финальная версия — листинг 9-13):

  ```rust
  trait Future {
      type Output;
      fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
  }
  ```

  `Future<Output = T>` читается как «когда-нибудь будет `T`» (в других языках это promise). Футура *разрешается* (resolves) в `T`, когда возвращает `Ready(T)`.
- **Футуры ленивы**: вызов `async fn` ничего не выполняет, а только создаёт значение-футуру. Работа начинается при первом `poll`.
- После `Ready` футуру опрашивать нельзя: она вправе запаниковать. Футура, которую можно безопасно опрашивать после `Ready`, называется **слитой** (fused).

### Пример 1.1 — футура вручную: `Countdown`

```rust
pub struct Countdown { left: u32, value: u32 }

impl Future for Countdown {
    type Output = u32;
    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<u32> {
        if self.left == 0 {
            return Poll::Ready(self.value);
        }
        self.left -= 1;
        cx.waker().wake_by_ref(); // контракт poll: вернули Pending => устроить wake
        Poll::Pending
    }
}

// Опрашиваем руками, Waker-пустышка:
let mut cx = Context::from_waker(Waker::noop());
loop {
    match Pin::new(&mut cd).poll(&mut cx) { /* ... */ }
}
// poll #1: Pending
// poll #2: Pending
// poll #3: Pending
// poll #4: Ready(42)
```

**Разбор.** Это и есть «неблокирующий интерфейс» в чистом виде: каждый вызов `poll` немного продвигает работу и возвращает управление. Обратите внимание на `wake_by_ref()` перед `Pending`. Без него настоящий исполнитель никогда не опросил бы футуру повторно (раздел 4). `Pin::new` здесь безопасен, потому что `Countdown` — `Unpin` (раздел 3). Цикл с `Waker::noop()` — это та самая «прожигающая CPU» петля, от которой книга предостерегает. Дальше мы её заменим.

### Пример 1.2 — футуры ленивы; первый `block_on`

```rust
async fn say(msg: &str) -> usize { println!("выполняется say"); msg.len() }

let fut = say("ленивая");      // ничего не напечатано!
let n = block_on(fut);         // вот теперь — «выполняется say»

let (v, polls, wakes) = block_on_stats(Countdown::new(3, 7));
// Countdown(3): 7, опросов 4, пробуждений 3
```

**Разбор.** `block_on` из `src/c9.rs` — минимальный исполнитель для одной футуры. Он закрепляет её на стеке (`pin!`), создаёт `Waker`, который будит текущий поток (`thread::unpark`), и крутит цикл «poll → если Pending, `thread::park()`». Поток спит, пока его не разбудит `wake`. Число пробуждений (3) совпадает с числом `Pending`: каждый `Pending` сопровождается ровно одним `wake`.

### Пример 1.3 — опрос после `Ready`

```rust
let mut fut = pin!(async { 1 });
assert_eq!(fut.as_mut().poll(&mut cx), Poll::Ready(1));
fut.as_mut().poll(&mut cx); // паника: `async fn` resumed after completion
```

**Разбор.** Футуры, которые компилятор генерирует из `async`, не слитые. Последнее состояние их машины — «Returned», и повторный опрос паникует. Комбинаторам вроде `select` в цикле поэтому нужна обёртка `Fuse` (задание 1.3).

## 2. Машины состояний, async/await и генераторы

### Теория

- Каждый вызов `poll` начинается **с начала** функции. Поэтому футура должна хранить, *где* она остановилась и *что* к этому моменту насчитала. Ручная футура — это **машина состояний**: `enum`, у которого по варианту на каждую точку ожидания (листинг 9-4). Писать такое больно: нужны `Option::take()` ради borrow checker, нужно знать конкретные типы вложенных футур (с `impl Future` их не назвать), а методы вынуждены забирать `self` по значению.
- `async`/`await` (Rust 1.39) генерирует эту машину за вас. Внутри используются **генераторы**: функция, которая умеет *уступать* (`yield`) посреди выполнения и потом продолжать с того же места (листинг 9-6). Компилятор переносит живые локальные переменные из стека в поля сгенерированной структуры: `x` превращается в `self.x`.
- `expr.await` ≈ `loop { match expr.poll(cx) { Ready(r) => break r, Pending => yield } }`, а `yield` из футуры — это `return Poll::Pending` с сохранённым состоянием.
- Главное отличие от ручной версии: borrow checker проверяет `async`-код **до** превращения в машину состояний. Поэтому ссылки **можно держать через `await`** (`rx.next()` берёт `&mut self`, а не `self`). Цена этого — футура становится **самоссылочной** (раздел 3).
- **Размер генератора** = максимум по точкам `await` от суммы переменных, живых в этой точке, включая ожидаемую вложенную футуру. Вложенные `async fn` раздувают футуры незаметно, и это видно в профиле как большой `memcpy`. Лечится так: держать меньше состояния через `await` или класть тяжёлую футуру в кучу через `Box::pin` (одна аллокация + косвенность). Сначала измерьте.

### Пример 2.1 — одна логика двумя способами

```rust
async fn two_steps() -> u32 {
    let a = Countdown::new(2, 10).await;
    let b = Countdown::new(1, 20).await;
    a + b
}

// Ручной эквивалент — машина состояний (ср. листинг 9-4):
enum TwoSteps {
    First(Countdown),
    Second { a: u32, fut: Countdown },   // `a` пережила точку ожидания
    Done,
}

impl Future for TwoSteps {
    type Output = u32;
    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<u32> {
        loop {                                   // аналог `return self.poll()` (❻)
            match &mut *self {
                TwoSteps::First(fut) => match Pin::new(fut).poll(cx) {
                    Poll::Ready(a) => *self = TwoSteps::Second { a, fut: Countdown::new(1, 20) },
                    Poll::Pending => return Poll::Pending,
                },
                TwoSteps::Second { a, fut } => match Pin::new(fut).poll(cx) {
                    Poll::Ready(b) => { let sum = *a + b; *self = TwoSteps::Done; return Poll::Ready(sum); }
                    Poll::Pending => return Poll::Pending,
                },
                TwoSteps::Done => panic!("опрошена после Ready"),
            }
        }
    }
}
// async fn:       30, опросов 4
// ручная машина:  30, опросов 4
```

**Разбор.** Число опросов совпадает: компилятор строит по сути тот же `enum`. Посмотрите на `loop`. Когда первая футура разрешилась, мы *в том же вызове* `poll` начинаем вторую. Если вернуть `Pending`, не опросив её, контракт `poll` будет нарушен: никто не вызовет `wake` (книга, примечание к ❻). Переменная `a` пережила точку ожидания, поэтому она стала полем варианта `Second`. Именно так генератор хранит локальные переменные.

### Пример 2.2 — размер футур

```rust
async fn big_across_await() -> u8 {
    let buf = [1u8; 8192];
    yield_now().await;          // buf жив через await => хранится в футуре
    buf[0]
}
async fn big_before_await() -> u8 {
    let x = { let buf = [1u8; 8192]; buf[0] };   // buf умер до await
    yield_now().await;
    x
}
async fn nested()       -> u8 { big_across_await().await + 1 }
async fn nested_boxed() -> u8 { Box::pin(big_across_await()).await + 1 }

// Countdown:                  8 байт
// two_steps():               16 байт
// big_across_await():      8194 байт
// big_before_await():         3 байт
// nested():                8195 байт   <- внутренняя футура целиком внутри
// nested_boxed():            16 байт   <- только Pin<Box<..>> + служебное
```

**Разбор.** Это врезка «Размер генераторов» в цифрах. Одно и то же «тяжёлое» тело даёт 8 КиБ или 3 байта в зависимости только от того, пересекает ли переменная `await`. `nested` показывает, как размер растёт по цепочке вызовов: каждая обёртка содержит в себе всю ожидаемую футуру. Такую футуру будут копировать при каждом перемещении. `Box::pin` превращает 8 КиБ в указатель.

### Пример 2.3 — ссылка через `await`

```rust
let fut = async {
    let arr = [1, 2, 3];
    let first = &arr[0];    // ссылка на поле самой футуры...
    yield_now().await;      // ...переживает точку уступания
    *first + arr.len() as i32
};
println!("{}", block_on(fut)); // 4
```

**Разбор.** В ручной машине состояний так сделать нельзя: поле `first` указывало бы на поле `arr` той же структуры. С `async` это компилируется, потому что borrow checker видит обычный линейный код. Но футура теперь **самоссылочная**: если её переместить *после* первого `poll`, `first` будет указывать в старое место. Как раз эту дыру закрывает `Pin`.

## 3. Pin и Unpin

### Теория

- **Проблема.** Генератор может хранить ссылки на собственные поля (пример 2.3). Перемещение в Rust — это `memcpy`, и ссылки внутри при нём не обновляются. Значит, после первого `poll` такую футуру нельзя двигать.
- **`Pin<P>`** оборачивает **указатель** `P` (`Pin<&mut T>`, `Pin<Box<T>>`), а не сам `T`. Иначе перемещение самого `Pin` переместило бы и `T`. Контракт такой: *значение за `Pin` больше никогда не переместится* (до своего `drop`). Отсюда сигнатура `poll(self: Pin<&mut Self>, ...)` (листинг 9-8).
- Ключевые методы (листинг 9-9). `Pin::new_unchecked` и `get_unchecked_mut` — `unsafe`: компилятор не может проверить, что вы не переместите `T` через `&mut T` (например, через `mem::swap`). Это касается и реализаций `Deref`/`DerefMut`/`Drop` у `P`. `Deref` (выдача `&T`) — безопасен. `Pin::set` безопасно заменяет значение на месте, потому что старое дропается внутри и наружу не выходит.
- **`Unpin`** — авто-трейт (как `Send`/`Sync`). Он означает: «мне всё равно, двигают ли меня, даже если я был закреплён». Для `T: Unpin` есть безопасные `Pin::new`, `DerefMut` и `into_inner` (листинг 9-10). Почти все типы — `Unpin`. Исключения — генераторы (`async`-футуры), `PhantomPinned` и всё, что их содержит.
- **Как получить `Pin`.**
  - *В куче*: `Box::pin(x)`, безопасно. Двигается `Box`, а `T` остаётся на месте. Поэтому `Box<T>: Unpin` для **любого** `T`, но достать `T: !Unpin` из `Pin<Box<T>>` всё равно нельзя.
  - *На стеке*: без аллокации и работает в `no_std`. Нужен `unsafe` с затенением переменной (макрос `pin_mut!`, листинг 9-11). Сегодня в std есть `std::pin::pin!`.
- `.await` разворачивается в `match expr { mut pinned => loop { unsafe { Pin::new_unchecked(&mut pinned) }.poll(cx) ... } }` (листинг 9-12). Это безопасно: `pinned` живёт внутри уже закреплённого генератора и доступен только через этот `Pin`.
- `Pin` не привязан к `Future`. Он годится для любой самоссылочной структуры.

### Пример 3.1 — самоссылка: без `Pin` и с ним

```rust
struct Naive { data: String, ptr: *const String }

struct Pinned { data: String, ptr: *const String, _pin: PhantomPinned }

impl Pinned {
    fn new(data: &str) -> Pin<Box<Self>> {
        let mut boxed = Box::pin(Pinned { data: data.into(), ptr: ptr::null(), _pin: PhantomPinned });
        let ptr: *const String = &boxed.data;
        // SAFETY: только записываем поле, значение из Pin не перемещаем.
        unsafe { boxed.as_mut().get_unchecked_mut().ptr = ptr };
        boxed
    }
}

// Naive до перемещения:   &data = 0x7fff…1f20, ptr = 0x7fff…1f20
// Naive после:            &data = 0x5a14…5ae0, ptr = 0x7fff…1f20  <- висячий
// Pinned:                 &data = 0x5a14…5a10, ptr = 0x5a14…5a10
// Pinned после move:      &data = 0x5a14…5a10, ptr = 0x5a14…5a10
```

**Разбор.** `Naive` после `Box::new(a)` переехала со стека в кучу, а `ptr` по-прежнему смотрит на стек. Разыменовать его — UB. У `Pinned` при `let moved = p` переезжает только `Pin<Box<_>>`, то есть указатель. Сама структура стоит на месте, поэтому `ptr` валиден. Попытка `mem::swap(&mut *a, &mut *b)` не компилируется: `Pinned: !Unpin`, значит у `Pin` нет `DerefMut`.

### Пример 3.2 — кто `Unpin`, а кто нет

```rust
fn assert_unpin<T: Unpin>(_: &T) {}

assert_unpin(&Countdown::new(1, 5));       // OK: все поля Unpin
let fut = async { yield_now().await; 1 };
// assert_unpin(&fut);                     // ОШИБКА: async-блок — !Unpin
// Pin::new(&mut fut);                     // та же ошибка

let boxed = Box::pin(fut);                 // закрепление в куче
assert_unpin(&boxed);                      // Pin<Box<T>>: Unpin всегда
let on_stack = pin!(async { 2 });          // закрепление на стеке: Pin<&mut {async}>
assert_unpin(&on_stack);                   // Pin<&mut T>: тоже Unpin
```

**Разбор.** `Unpin` выводится из полей так же, как `Send`/`Sync` (глава 3, маркерные трейты). `async`-блоки всегда `!Unpin`, даже без ссылок через `await`: компилятор не анализирует это, а консервативно запрещает. Обёртки `Pin<Box<T>>` и `Pin<&mut T>` сами `Unpin`, ведь двигается только указатель. Поэтому `Box::pin(fut)` — универсальный способ получить `Unpin`-футуру, которую можно передать туда, где требуется `F: Future + Unpin`.

### Пример 3.3 — `pin_mut!` из книги и `Pin::set`

```rust
macro_rules! pin_mut {
    ($var:ident) => {
        let mut $var = $var;                                       // забрали значение
        let mut $var = unsafe { Pin::new_unchecked(&mut $var) };   // затенили имя
    };
}

let fut = async { yield_now().await; yield_now().await; 3 };
pin_mut!(fut);                     // fut: Pin<&mut {async block}>
while fut.as_mut().poll(&mut cx).is_pending() {}

let mut p = Box::pin(two_steps());
let _ = p.as_mut().poll(&mut cx);  // начали выполнять
p.set(two_steps());                // заменили на месте — это безопасно
```

**Разбор.** Обе строки макроса нужны. Без первой можно было бы написать `{ pin_mut!(foo); ... }` во вложенной области, а после неё снова пользоваться незакреплённым `foo` (пример в книге). Вторая затеняет имя, и до незакреплённого значения уже не добраться. Обратите внимание на `fut.as_mut()`: `poll` поглощает `Pin<&mut Self>`, а `as_mut` перезаимствует его для каждого вызова. `Pin::set` работает, потому что старое значение дропается внутри `set` и наружу не попадает.

## 4. Засыпание: Waker и контракт poll

### Теория

- **Исполнитель** (executor) опрашивает футуры. Чтобы не крутить вхолостую, ему нужно знать, *когда* опрашивать снова. Для этого `poll` получает `&mut Context`, внутри которого лежит **`Waker`** (листинг 9-13).
- **Контракт `poll`.** Вернула `Pending` — обязана гарантировать, что *кто-то* вызовет `wake` на этом `Waker`, когда можно будет продвинуться. Составные футуры выполняют его «бесплатно»: они возвращают `Pending` только тогда, когда `Pending` вернул ребёнок. Настоящую работу делают **листовые футуры** (leaf futures):
  - *внутренние события* (канал в памяти): сохранить `Waker` в разделяемом состоянии, и отправитель вызовет `wake`;
  - *внешние события* (сокет, таймер, диск): обычно через **реактор** исполнителя. Листовая футура регистрирует источник события и свой `Waker`. Когда работы нет, исполнитель делает один большой блокирующий вызов (`epoll`/`kqueue`/IOCP) и будит `Waker`'ы тех, у кого что-то произошло. Отдельный поток на каждое ожидание — расточительный вариант (наш `Delay` устроен так ради простоты).
- `Waker` — это **ручная vtable** (`RawWakerVTable`: `clone`, `wake`, `wake_by_ref`, `drop`) плюс сырой указатель на данные. По сути динамическая диспетчеризация из главы 3. Что делает `wake`, решает тот, кто создал `Waker`, то есть исполнитель. На практике проще реализовать трейт `std::task::Wake` для `Arc<T>`.
- **«Пробуждение» — неточное название.** На самом деле `wake` означает «эта задача **готова к выполнению**» (runnable). Будить спящий поток — лишь побочный эффект. Исполнитель знает, кто готов: значит, он знает, когда можно спать, и опрашивает только нужные задачи, а не тысячи.
- Листовые футуры привязаны к своему реактору. `TcpStream` от одного рантайма не работает без этого рантайма. Библиотекам лучше быть обобщёнными: `T: AsyncRead + AsyncWrite`.
- **Субисполнители** (`join`, `select`) содержат несколько дочерних футур. Чтобы не опрашивать всех подряд, они **оборачивают** полученный `Waker`: свой `wake` помечает конкретного ребёнка как готового и вызывает исходный.
- **Не блокируйте в async-коде.** `std::thread::sleep`, тяжёлые вычисления и плотные циклы без `await` занимают поток исполнителя, и остальные задачи стоят. Эмпирическое правило: футура не должна работать дольше ~1 мс без возврата `Pending`.

### Пример 4.1 — листовая футура `Delay`

```rust
pub struct Delay { dur: Duration, started: bool, shared: Arc<Mutex<DelayState>> }
struct DelayState { done: bool, waker: Option<Waker> }

impl Future for Delay {
    type Output = ();
    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<()> {
        {
            let mut st = self.shared.lock().unwrap();
            if st.done { return Poll::Ready(()); }
            match &st.waker {                                // сохраняем АКТУАЛЬНЫЙ Waker
                Some(w) if w.will_wake(cx.waker()) => {}
                _ => st.waker = Some(cx.waker().clone()),
            }
        }
        if !self.started {                                   // ленивый старт
            self.started = true;
            let (shared, dur) = (self.shared.clone(), self.dur);
            thread::spawn(move || {                          // «внешнее событие»
                thread::sleep(dur);
                let mut st = shared.lock().unwrap();
                st.done = true;
                if let Some(w) = st.waker.take() { w.wake(); }
            });
        }
        Poll::Pending
    }
}
// Delay(100 мс): 100 мс, опросов 2, пробуждений 1
```

**Разбор.** Ровно 2 опроса: первый запускает таймер, второй приходит после единственного `wake`, и между ними поток исполнителя спит. Это ответ на вопрос из раздела 1 про цикл. Waker обновляется на каждом `poll`, потому что футуру могут переместить в другую задачу, и старый Waker будил бы не того. `will_wake` позволяет не клонировать, если Waker тот же.

### Пример 4.2 — Waker изнутри: vtable с логированием

```rust
fn logging_waker() -> Waker {
    fn clone(p: *const ()) -> RawWaker { println!("[vtable] clone"); RawWaker::new(p, &VTABLE) }
    fn wake(_: *const ())        { println!("[vtable] wake"); }
    fn wake_by_ref(_: *const ()) { println!("[vtable] wake_by_ref"); }
    fn drop_waker(_: *const ())  { println!("[vtable] drop"); }
    static VTABLE: RawWakerVTable = RawWakerVTable::new(clone, wake, wake_by_ref, drop_waker);
    unsafe { Waker::from_raw(RawWaker::new(std::ptr::null(), &VTABLE)) }
}
//   опрос Countdown(1):
//     [vtable] wake_by_ref          <- будит по ссылке, не храня
//   опрос Delay(50 мс):
//     [vtable] clone                <- Delay сохраняет свою копию
//     [vtable] wake                 <- из потока таймера, по значению (без drop!)
//   повторный опрос Delay: Ready(())
//   конец функции:
//     [vtable] drop                 <- дропается наш исходный waker
```

**Разбор.** Видно, как разные футуры обращаются с Waker'ом. `Countdown` будит сразу, по ссылке. `Delay` клонирует Waker и отдаёт копию другому потоку, а тот вызывает `wake`, поглощая её. Поэтому после `wake` нет `drop`: по контракту `RawWakerVTable` функция `wake` сама освобождает данные. Указатель `data` в настоящих исполнителях указывает на задачу. Так один и тот же код vtable различает задачи.

### Пример 4.3 — нарушение контракта: «забытый» wake

```rust
struct Forgetful { polled: bool }
impl Future for Forgetful {
    type Output = ();
    fn poll(mut self: Pin<&mut Self>, _cx: &mut Context<'_>) -> Poll<()> {
        if self.polled { return Poll::Ready(()); }
        self.polled = true;
        Poll::Pending                 // готова, но никому не сказала
    }
}
// Forgetful без wake:  None  <- без таймаута висели бы вечно
// Countdown c wake:    Some(1)
```

**Разбор.** Это самый частый баг ручных футур. Футура *уже готова* продолжить, но исполнитель об этом не знает и спит. В реальном коде такой баг выглядит как «иногда запрос висит, пока не придёт следующий»: футуру случайно будит чужое событие.

## 5. spawn: задачи и исполнитель

### Теория

- Футуры образуют **дерево**. Корень, который отдают исполнителю, называется **задачей** (task). Исполнитель знает только задачи. Внутрь дерева `poll` спускается по одному ребру за вызов, до листовых футур.
- Сервер, который делает `handle_client(stream).await` в цикле (листинг 9-14), обслуживает клиентов **по одному**. Если держать футуры клиентов в `Vec` и опрашивать вручную (листинг 9-15), получится свой кривой исполнитель внутри задачи: он крутится вхолостую, опрашивает всех подряд и привязан к одному потоку, потому что `poll` требует `&mut` на единственную задачу.
- **`spawn(fut)`** делает футуру **отдельной задачей** (листинг 9-16). Исполнитель мультиплексирует задачи сам. Многопоточный исполнитель может опрашивать разные задачи **параллельно**, если футуры `Send`.
- Задача похожа на поток, но она **не исполняется сама**: её кто-то должен опрашивать. Если исполнитель остановлен или дропнут, задачи замирают. Есть ли у исполнителя фоновые потоки, зависит от конкретного рантайма.
- Каждой задаче — свой `Waker`. Тогда `wake` знает, *какую* задачу вернуть в очередь готовых.

### Пример 5.1 — последовательный сервер против `spawn`

Мини-исполнитель из `src/c9.rs` (сокращённо):

```rust
struct Task { fut: Mutex<Option<BoxFuture>>, queue: mpsc::Sender<Arc<Task>> }

impl Wake for Task {
    fn wake(self: Arc<Self>) {            // wake = «задача готова» => в очередь
        let queue = self.queue.clone();
        let _ = queue.send(self);
    }
}

impl Executor {
    pub fn run(&self) {
        while self.spawner.live.load(SeqCst) > 0 {
            let task = self.ready.recv().unwrap();             // спим, пока нет готовых
            let Some(mut fut) = task.fut.lock().unwrap().take() else { continue };
            let waker = Waker::from(task.clone());             // свой Waker на задачу
            let mut cx = Context::from_waker(&waker);
            if fut.as_mut().poll(&mut cx).is_pending() {
                *task.fut.lock().unwrap() = Some(fut);
            } else {
                self.spawner.live.fetch_sub(1, SeqCst);
            }
        }
    }
}
```

## Шпаргалка по главе

- **Асинхронность** = «готово или приходи позже» (`Poll::Ready(T)` / `Poll::Pending`). Async даёт **конкурентность** (`_-_-_-`) без обязательного **параллелизма** (`=====`).
- **`Future::poll(self: Pin<&mut Self>, cx: &mut Context) -> Poll<Output>`**. Футуры **ленивы** и ничего не делают до первого `poll`. После `Ready` опрашивать нельзя: если футура не слитая (fused), будет паника.
- **async/await** = машина состояний, сгенерированная компилятором (генератор). Живые через `await` переменные становятся полями. `await` ≈ `loop { poll; yield }`. Ссылки через `await` можно держать, но футура становится самоссылочной.
- **Размер футуры** = максимум по точкам `await` от суммы живого состояния, включая вложенные футуры целиком. Большие футуры — это `memcpy` в профиле. Лечится через `Box::pin` или уменьшение состояния, но сначала измерьте.
- **`Pin<P>`** — «значение за указателем `P` больше не переместится». Для `T: !Unpin` не бывает безопасного `&mut T`. **`Unpin`** — авто-трейт «мне можно двигаться»: для него безопасны `Pin::new`, `DerefMut`, `into_inner`. `async`-блоки и `PhantomPinned` — `!Unpin`.
- **Закрепление**: `Box::pin` (куча, безопасно, `Box<T>: Unpin` всегда) или `pin!`/`pin_mut!` (стек, без аллокации, через затенение). `Pin::set` безопасно заменяет значение на месте. Pin-проекция на поле — `unsafe` с условиями.
- **Контракт poll**: вернул `Pending` — обеспечь будущий `wake`. Составные футуры наследуют его от детей, **листовые** реализуют сами: внутренние события через сохранённый Waker, внешние через **реактор** (`epoll` и т. п.). Сохраняйте **актуальный** Waker (`will_wake`).
- **`Waker`** — vtable (`clone`/`wake`/`wake_by_ref`/`drop`) + данные. `wake` означает «задача готова к выполнению», а не «разбуди поток». Удобный путь — `impl Wake for Arc<T>`.
- **Задача** — корень дерева футур. **`spawn`** делает футуру отдельной задачей. Только так исполнитель мультиплексирует (и, при `Send`, распараллеливает) работу. Задачи живут, пока работает исполнитель.
- **Субисполнители** (`join`/`select`) оборачивают Waker, чтобы опрашивать только разбуженных детей.
- **Не блокируйте** поток исполнителя: никакого `thread::sleep`, тяжёлых вычислений или циклов без `await`. Примерно 1 мс без `Pending` — максимум. Блокирующее уносите на отдельный поток (`spawn_blocking`).
- Листовые футуры привязаны к своему рантайму. Переносимые библиотеки обобщают по `AsyncRead`/`AsyncWrite`.
