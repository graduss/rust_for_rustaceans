## Урок 1. Футуры и `async`/`await` (17.1)

### Теория
- `async fn` при вызове **не выполняет тело**, а возвращает футуру — машину состояний в начальном состоянии. Тело работает, только когда футуру опрашивает рантайм (`rt::block_on`).
- `async fn f(x: &str) -> T` — это сахар для `fn f(x: &str) -> impl Future<Output = T>` с телом `async move { ... }`.
- `move` нужен, потому что блок захватывает аргумент: без него блок заимствовал бы локальную переменную функции, которая умирает раньше футуры.
- Edition 2024: `Future` есть в прелюдии; `impl Trait` в возврате сам захватывает времена жизни аргументов (в 2021 нужно было `+ '_`).
- Внутри одной футуры `.await` идут **строго по очереди** — это ещё не конкурентность.
- `async { ... }` — выражение-футура; удобно передавать в `block_on`.
- `rt::sleep(d)` не блокирует поток, а отдаёт управление рантайму.
- `rt::select(a, b)` — гонка: результат `Either::Left`/`Right` от первой готовой футуры, проигравшая **дропается** (так в Rust выглядит отмена).

## Урок 2. Конкурентность: `spawn_task` и `join` (17.2)

### Теория
- `rt::spawn_task(fut)` отдаёт футуру рантайму как отдельную задачу (аналог `thread::spawn`, но лёгкий). Возвращает `JoinHandle` — футуру с `Output = Result<T, _>`.
- `block_on` **не ждёт** фоновых задач: когда главная футура завершилась, незаконченные задачи дропаются. Нужен результат — `handle.await`.
- `rt::join(a, b)` опрашивает обе футуры по очереди в одной задаче и возвращает `(a, b)`. Порядок опроса фиксирован → вывод детерминирован.

### Задание 2.1 ⏳
Задержка 50 мс.
1. `f2_1` — `spawn_task` с циклом `1..10` ("first task"), в главной футуре цикл `1..5` ("second task"), handle не сохранять. Ожидание: первая задача обрывается на ~4–5.
2. `f2_2` — то же, но `handle.await.unwrap()` в конце. Ожидание: досчитывает до 9.
3. `f2_3` — без задач: `fut1` (до 10) и `fut2` (до 5) через `rt::join(fut1, fut2).await`. Ожидание: строгое чередование, потом остаток first.
